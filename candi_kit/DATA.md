# DATA.md — the input contract

This is the document to read before you point the kit at your own data. It specifies the on-disk
directory the bake expects, how the four covariates are derived, what the sentinels mean, the panel
file, the HDF5 schema the bake writes, and the traps — each with the symptom you will actually see.

Everything here is sourced from the kit's own code. Citations are `path:line` relative to
`candi_kit/`. The one exception is `METADATA_AUDIT.md` (§6.7, §6.8), which is a research document
rather than code; it ships at [`research/METADATA_AUDIT.md`](research/METADATA_AUDIT.md).

**No checkpoints ship with this kit.** You bake an HDF5 from your data and train from scratch.

---

## 0. The pipeline in one line

```
ENCODE-style directory  --[prep.bake]-->  HDF5 (schema v2, self-describing)  --[dataset]-->  batches  --[train]-->  ckpt + results.json
```

Scale flows one way only: `panel.json` → handler → **derived** assay order → `h5.attrs` → dataset →
`build_real_model`. `num_assays`, `context_bins`, `resolution`, `dsf_list`, the assay order and the
train/eval chromosomes are **properties of the baked file, never train-time flags**
(`src/candi_kit/dataset.py:129-145`). You cannot silently train an 8-assay model on a 12-assay file.

## 1. Expected on-disk layout

```
<ROOT>/
  aliases.json                       # generated by the kit on first bake if absent
  navigation.json                    # generated by the kit on first bake if absent
  .candi_kit_state/                  # kit-owned scratch (metadata.csv, split.json); auto-created
  <BIOSAMPLE>/                       # e.g. T_DND-41, V_DND-41, B_RWPE2  (prefix REQUIRED, see §1.2)
    <ASSAY>/                         # e.g. H3K4me3, DNase-seq, ATAC-seq
      file_metadata.json
      signal_DSF1_res25/
        chr1.npz ... chrX.npz
        metadata.json
      signal_DSF2_res25/  { chr*.npz, metadata.json }
      signal_DSF4_res25/  { chr*.npz, metadata.json }
      signal_DSF8_res25/  { chr*.npz, metadata.json }
      signal_BW_res25/    { chr*.npz }        # arcsinh-able -log10 p-value track
      peaks_res25/        { chr*.npz }        # 0/1 peak call mask
    chipseq-control/                 # optional but strongly recommended (see §3.3)
      file_metadata.json
      signal_DSF{1,2,4,8}_res25/ { chr*.npz, metadata.json }
```

> **`<ROOT>` must be WRITABLE.** The bake creates `aliases.json`, `navigation.json` and
> `.candi_kit_state/` inside the data root on first use. Pointing the kit at a shared, read-only
> reference corpus — the normal institutional setup — therefore fails. If you cannot get write access,
> copy or symlink the tree into a writable location first. (This is separate from the FASTA's own need
> for a writable parent so pysam can build its `.fai`.)

`res25` is literally `res{resolution}`; the directory name follows the `resolution` you set in the
panel (`src/candi_kit/prep/handler.py:942-943, 1027-1034, 1094-1096, 1154-1156, 1185-1187`).

### 1.1 The `.npz` files

Each `.npz` holds **one** array covering the **whole chromosome** at `resolution` bp per bin. Only
`data.files[0]` is read, so the array key is irrelevant (`src/candi_kit/prep/handler.py:863-869`).

| directory | dtype on disk | length (bins) | contents |
|---|---|---|---|
| `signal_DSF{d}_res25/chr*.npz` | integer (`int64` in the reference corpus) | **`ceil(chr_len / resolution)`** | **RAW, UNNORMALIZED read counts** per bin at downsampling factor `d` |
| `signal_BW_res25/chr*.npz` | `float32` | **`floor(chr_len / resolution)`** | -log10 p-value signal, untransformed on disk |
| `peaks_res25/chr*.npz` | integer | **`floor(chr_len / resolution)`** | 0/1 peak indicator |

The ceil/floor difference is real, not a typo. Measured on the reference EIC corpus:
`T_DND-41/H3K27me3/chr19` gives counts `2,344,705 = ceil(58,617,616/25)` while BW and peaks give
`2,344,704 = floor(...)`; the same holds on `T_H1-hESC/H3K4me1/chr1`
(`9,958,257` vs `9,958,256`). The loader never validates array length — it just slices
`[start // resolution : end // resolution]`
(`src/candi_kit/prep/handler.py:1073-1075, 1124-1134`). Tiled and cCRE-sampled windows are always
fully inside `floor(chr_len/resolution)`, so the off-by-one is benign for the kit's own window
generation, but an array that is short by more than one bin will silently yield a short slice and
then a shape error deep inside `make_region_tensor_*`.

Counts must be **raw integers**. Do not pre-transform them. `arcsinh` is applied inside the model
(§6.2).

### 1.2 Biosample names

The kit runs the handler in **EIC layout mode only** (`self.eic = True`,
`src/candi_kit/prep/handler.py:101`). `_filter_navigation` deletes every biosample directory whose
name does not start with `T`, `V` or `B` (`handler.py:875-878`), and the panel validator requires
the full `T_` / `V_` / `B_` prefix (`src/candi_kit/prep/panel.py:28-30`).

| prefix | role |
|---|---|
| `T_` | training biosample; also the denoising ground truth at eval |
| `V_`, `B_` | held-out views of the *same* cell type; supply the imputation ground truth (`src/candi_kit/dataset.py:209-218, 339-365`) |

`V_<X>` and `B_<X>` are matched to `T_<X>` by string suffix. `T_K562` ↔ `V_K562` / `B_K562`.

You need **≥ 2 `T_` biosamples, each with ≥ 2 available assays**. Below that the whole-assay cloze
masker skips the sample (`num_available <= 1`, `src/candi_kit/_vendored.py:131-134`) and the
imputation loss is identically zero. Both the panel (`panel.py:31-34`) and the bake
(`src/candi_kit/prep/bake.py:244-248`) assert this.

## 2. The three metadata sources and the four covariate rows

Every assay column carries a length-4 covariate vector. The metadata tensor is `[4, F]` per
biosample per DSF level, `[B, 4, F]` in a batch:

| row | field | dtype in tensor | source |
|---|---|---|---|
| 0 | `log2(sequencing depth)` | float | `signal_DSF{d}_res25/metadata.json` → key `depth`, **per DSF level** |
| 1 | `assay_id` | float holding an integer | derived from `aliases.json` order; **not read from any file** |
| 2 | `read_length` | float (bp) | `<ASSAY>/file_metadata.json` → `read_length` |
| 3 | `run_type` | float, `0` = single-end, `1` = paired-end | `<ASSAY>/file_metadata.json` → `run_type` |

Assembly site: `make_bios_tensor_Counts`, `src/candi_kit/prep/handler.py:1231-1295`.

**These four rows are raw. No normalization, no z-scoring.** They are fed to the model as-is
(`src/candi_kit/encoder.py:142-152`).

### 2.1 Source A — `signal_DSF{d}_res25/metadata.json` (per DSF level)

```json
{"coverage": 0.3173361622168517, "depth": 24684534, "dsf": 1}
```

Only `depth` is read (`handler.py:1054-1057`). Row 0 is `log2(depth)`. Because depth is per-DSF,
`meta_dsf{d}[0] == meta_dsf1[0] - log2(d)` holds to within a small tolerance, and the bake asserts
it at `< 0.05` for every available column (`src/candi_kit/prep/bake.py:415-425`). This is the
invariant that catches a DSF-1 file masquerading as DSF-8.

### 2.2 Source B — `<ASSAY>/file_metadata.json` (per experiment)

**Every value in this file is a dict keyed by replicate index**, not a scalar:

```json
{
  "assay":        {"2": "H3K4me3"},
  "accession":    {"2": "ENCFF764MJJ"},
  "read_length":  {"2": 36},
  "run_type":     {"2": "single-ended"},
  "sequencing_platform": {"2": "Illumina HiSeq 2500"},
  "lab":          {"2": "Bradley Bernstein, Broad"}
}
```

The key (`"2"` here) is arbitrary; for assays the code takes `list(d.keys())[0]`
(`handler.py:1262-1264, 1272`). The kit asserts `len(run_type) == 1` so the arbitrary-key read is
well-defined (`handler.py:1258-1261`). **`read_length` is not covered by that assert** — if your
`file_metadata.json` holds more than one replicate under `read_length`, one is picked
non-deterministically. Emit exactly one replicate per experiment.

`run_type` parsing is substring-based (`handler.py:1262-1271`): the string must contain `single`
or `pair`. Anything else raises. Only `sequencing_platform` and `lab` are unused — they are read
into the dict and dropped.

For the **control** track the replicate key is hard-coded to `"2"`
(`handler.py:1217-1222`), with silent fallbacks: missing `read_length` → `None` → `50`
(`handler.py:1350`), missing `run_type` → `"single-ended"` → `0` (`handler.py:1348-1349`). If your
control metadata is keyed differently you will get depth right and read_length/run_type wrong,
with no warning.

### 2.3 Source C — `aliases.json` (the assay_id, and the column order)

`assay_id` is the **index of the assay in `aliases['experiment_aliases']` key order**
(`handler.py:188-190`), and the **control uses `assay_id == num_assays`**, one past the last real
assay (`handler.py:197`, `src/candi_kit/prep/reference_sample.py:51-52`). The same order is the
column order of every `[*, *, F]` array in the HDF5.

`aliases.json` is generated on first bake if absent (`handler.py:288-316`) by listing
`<ROOT>/<BIOSAMPLE>/<ASSAY>/` directories and ordering assays by **descending biosample
availability**. See §4 for why this order can only be derived and recorded, never declared.

## 3. Sentinels, masking, and the `obs`/`imp` naming

### 3.1 Sentinel values

| value | name | meaning |
|---|---|---|
| `-1` | `MISSING` | this assay is not available for this biosample |
| `-2` | `CLOZE` | this assay is available but has been masked out for this training step |

Defined once in `src/candi_kit/_vendored.py`; imported everywhere else. They are written into
`x_data`, `x_meta` and `x_avail` alike (`_vendored.py:146-148`).

The encoder gives each sentinel its **own learned embedding per field** — it does not treat `-1`
as the number minus one (`src/candi_kit/encoder.py:94-106`):

* continuous fields (depth, read_length): `depth_missing_emb`, `depth_cloze_emb`,
  `readlen_missing_emb`, `readlen_cloze_emb` — separate `nn.Parameter`s substituted after the
  linear projection (`encoder.py:118-133`);
* categorical fields (assay_id, run_type): the embedding tables are sized `num_assays + 3` and
  `num_runtypes + 2`, with the last two rows reserved for MISSING and CLOZE
  (`encoder.py:102-105, 160-179`).

Consequence: `assay_id` must lie in `[0, num_assays]` and `run_type` in `[0, num_runtypes-1]`
(2 levels). Values above those bounds would silently alias onto the sentinel slots, so the kit
raises instead (`encoder.py:161-167, 181-187`).

### 3.2 `obs` vs `imp` means **unmasked vs masked**

This trips up every new reader. Throughout this codebase — losses, metric keys, result JSON —

* **`obs` / `observed_map` = positions that were NOT masked this step**
* **`imp` / `masked_map` = positions that WERE masked this step**

They do **not** mean biologically observed vs biologically imputed. See
`src/candi_kit/batch.py:68-71`. `imp` metrics in the results file are the model's performance on
whole assays that were cloze-masked out of its input.

### 3.3 The control channel is index `A` and is never masked

`prepare_masked_batch` applies the masker to the `F` assay columns first, and only then
concatenates the control column onto the end (`src/candi_kit/batch.py:65-66` then `:121-123`):

```
x_data_in = cat([x_data_masked, control_data], dim=2)   # -> [B, L, F+1], control at index F
x_meta_in = cat([x_meta_masked, control_meta], dim=2)   # -> [B, 4, F+1]
```

The control is therefore **structurally unmaskable** — it is always available to the model. Its
covariate row 1 carries `control_assay_id = num_assays` (§2.3). The bake refuses a biosample whose
control is not available in 100% of windows unless you pass `--allow-missing-control`
(`src/candi_kit/prep/bake.py:437-444`).

## 4. The panel selection file

One flat JSON file; every field is consumed. Strict unknown-key rejection
(`src/candi_kit/prep/panel.py:51-57`).

### 4.1 Schema

| key | type | default | notes |
|---|---|---|---|
| `assays` | `list[str]` | **required** | **order-insensitive** (see §4.2). Must be unique and non-empty. |
| `biosamples` | `list[str]` | **required** | full names with `T_`/`V_`/`B_` prefix; ≥ 2 `T_` |
| `dsf_list` | `list[int]` | `[1,2,4,8]` | load-bearing; a single level makes DSF sampling inert and deletes the depth signal |
| `resolution` | `int` | `25` | must be a perfect square — it is `dna_pool_size**2` |
| `context_bins` | `int` | `768` | must be divisible by 8 (`pool_size ** n_cnn_layers`) |
| `train_chroms` | `list[str]` | `["chr19"]` | must be disjoint from `eval_chroms` |
| `eval_chroms` | `list[str]` | `["chr21"]` | |

Required DNA length per window is `context_bins * resolution` bp; the encoder asserts it at forward
time.

### 4.2 The assay ORDER is derived from the data, never declared

`configs/panel.q19.json` lists the eight assays in a human-friendly order:

```json
{
  "assays": ["ATAC-seq","DNase-seq","H3K4me3","H3K4me1","H3K27ac","H3K27me3","H3K36me3","H3K9me3"],
  "biosamples": ["T_DND-41","T_H1-hESC","T_H9","T_RWPE2","T_heart_left_ventricle",
                 "V_DND-41","V_H1-hESC","V_heart_left_ventricle","B_DND-41","B_RWPE2"],
  "dsf_list": [1,2,4,8], "resolution": 25, "context_bins": 768,
  "train_chroms": ["chr19"], "eval_chroms": ["chr21"]
}
```

**That is not the column order of the resulting HDF5.** The true column order is the post-filter
key order of `aliases['experiment_aliases']`
(`src/candi_kit/prep/reference_sample.py:56-58`), which `_make_alias` establishes as
`data_matrix.count().sort_values(ascending=False)` — assays sorted by how many biosample
directories contain them (`src/candi_kit/prep/handler.py:302`). For the reference EIC panel
that resolves to:

```
[DNase-seq, H3K4me3, H3K36me3, H3K27ac, H3K9me3, H3K27me3, H3K4me1, ATAC-seq]
```

**Why it can only be derived.** That sort is (a) data-dependent, (b) unstable on ties — pandas'
default sort is quicksort — and (c) seeded by `os.listdir` order. Two bakes of the same directory
on different filesystems can legitimately produce different orders. So the kit derives the order,
records it in `h5.attrs['assays']`, and asserts a bijection against the requested panel:

```python
# src/candi_kit/prep/reference_sample.py:43-52
absent  = sorted(set(panel.assays) - present)         -> ValueError naming the assays
missing/extra vs resolve_column_order(h)              -> ValueError naming both sets
[h.assay_to_id[a] for a in resolved] != range(A)      -> ValueError
h.control_assay_id != len(resolved)                   -> ValueError
```

**No assay-name list literal exists anywhere in `candi_kit`.** Every consumer — dataset, eval,
report — reads `h5.attrs['assays']`.

**Concrete symptom of getting it wrong.** The model only ever sees the integer `assay_id`, so a
permuted name list does not crash and does not change the loss — it mislabels every per-assay
number in the results and every metadata join. In the research history this was measured: joining
the eight assay columns of the baked file against the ENCODE metadata (depth, read_length,
run_type triples) matched **38/38 experiments under the handler-derived order and 5/38 under a
hand-written list**, with only one of the eight positions coincidentally correct
(`sandbox/diagnostics/dual_conditioning_real/METADATA_AUDIT.md:109-113`). For an 8-assay panel
there are `8! = 40,320` orderings and only the derived one joins cleanly. If you see per-assay
CRPS or Spearman that is inexplicably assigned to the wrong marks, this is why — but in this kit
the bijection assert fires first.

## 5. The bake

### 5.1 Prerequisites (side files — you must download these)

These are **not** in this kit and **not** in the data directory. They are standard public reference
files; get them from UCSC. This is the one thing you must fetch from the internet before you can bake.

```bash
mkdir -p side && cd side

# 1. Chromosome sizes (~12 KB) — always required.
wget https://hgdownload.soe.ucsc.edu/goldenPath/hg38/bigZips/hg38.chrom.sizes

# 2. Reference genome — always required. TWO OPTIONS:

#    (a) Only the chromosomes you actually use. Far smaller and faster, and enough
#        unless you enable type2 loci (below). For the default chr19-train / chr21-eval panels:
for c in chr19 chr21; do
  wget -qO- https://hgdownload.soe.ucsc.edu/goldenPath/hg38/chromosomes/$c.fa.gz | zcat
done > hg38_subset.fa
grep -E '^(chr19|chr21)\s' hg38.chrom.sizes > hg38_subset.chrom.sizes

#    (b) The whole genome (3.27 GB compressed source) — required if you use --type2-ccre/--type2-non,
#        because those sample loci from every chromosome EXCEPT your train/eval ones.
# wget https://hgdownload.soe.ucsc.edu/goldenPath/hg38/bigZips/hg38.fa.gz && gunzip hg38.fa.gz

# 3. cCRE regions (~61 MB) — ONLY if you use --type2-ccre / --type2-non.
wget -O GRCh38-cCREs.bed https://downloads.wenglab.org/Registry-V3/GRCh38-cCREs.bed
```

**You only need the chromosomes in `train_chroms ∪ eval_chroms`** unless you turn on type2 loci. A
2-chromosome FASTA is ~107 MB instead of 3.27 GB and bakes noticeably faster. The bake fails loudly with
a missing-chromosome error if the FASTA is short of what the panel asks for, so this is safe to try.

| flag | required | size | notes |
|---|---|---|---|
| `--chrom-sizes` | yes | ~12 KB | two columns, `chrom\tlength`. Must contain every chromosome in the panel. |
| `--fasta` | yes | 107 MB (2 chroms) – 3.27 GB (all) | needs a `.fai` beside it, or a writable parent so pysam can build one (`src/candi_kit/prep/paths.py:22-24`). **There is no counts-only path that skips DNA** — the encoder always builds and calls the DNA tower. |
| `--blacklist` | no | — | plain BED, `chrom start end`; `#` comments skipped (`handler.py:211-233`). See §6.5. |
| `--ccres` | only if `--type2-ccre`/`--type2-non` > 0 | 61 MB | 6-column BED. Requires a whole-genome FASTA (see above). |

> **Genome build.** Everything here assumes **hg38 / GRCh38**, matching `DATA_CANDI_EIC`. If your counts
> were called against a different build, you must supply the matching FASTA and chrom-sizes — nothing in
> the kit detects a mismatch, and the DNA tower would silently read the wrong sequence.

### 5.2 CLI

```bash
python -m candi_kit.prep.bake \
  --root        /path/to/ENCODE_STYLE_ROOT \
  --panel       candi_kit/configs/panel.q19.json \
  --out         /scratch/$USER/candi_kit/panel_q19.h5 \
  --fasta       /path/to/hg38.fa \
  --chrom-sizes /path/to/hg38.chrom.sizes \
  --blacklist   /path/to/hg38_blacklist_v2.bed \
  --seed 42
```

Optional: `--ccres FILE --type2-ccre N --type2-non N` (adds cCRE-centred and random non-cCRE
training loci, and writes a `<stem>_loci_type2.bed` sidecar);
`--max-tile-per-chrom N` / `--max-windows N` (smoke runs);
`--allow-missing-control`. Full parser: `src/candi_kit/prep/bake.py:447-462`.

A quick smoke bake that finishes in minutes:

```bash
python -m candi_kit.prep.bake \
  --root /path/to/ROOT --panel candi_kit/configs/panel.example.json \
  --out /scratch/$USER/candi_kit/smoke.h5 \
  --fasta /path/to/hg38.fa --chrom-sizes /path/to/hg38.chrom.sizes \
  --max-tile-per-chrom 200
```

`--out` has **no default and must point at `/scratch`** (or any large scratch filesystem). See
§5.5.

### 5.3 What it writes — HDF5 schema v2

Let `n` = number of windows, `L = context_bins`, `Lbp = L * resolution`, `F = len(assay_order)`.
All per-biosample datasets are chunked `(1, ...)` with gzip level 1
(`src/candi_kit/prep/bake.py:290-380`).

**Root attrs** (`bake.py:292-305`):

| attr | type | value |
|---|---|---|
| `version` | int | `2` — the dataset **refuses** v1 files (`dataset.py:130-134`) |
| `context_bins` | int | `L` |
| `resolution` | int | bp per bin |
| `data_root` | str | the `--root` you baked from |
| `kit_version` | str | `candi_kit.__version__` |
| `assays` | json `list[str]` | **the derived column order** — the authority |
| `assay_ids` | json `list[int]` | `[0 .. F-1]`, asserted |
| `requested_panel` | json `list[str]` | what you wrote in `panel.json` |
| `num_assays` | int | `F` |
| `control_assay_id` | int | `F` |
| `dsf_list` | json `list[int]` | the DSF ladder |
| `train_chroms`, `eval_chroms` | json `list[str]` | |
| `panel_json` | json | the full panel, verbatim |

**Windows** — each `(n,)` (`bake.py:307-312`):

| dataset | dtype | notes |
|---|---|---|
| `/windows/chrom` | vlen utf-8 str | |
| `/windows/start` | `int64` | bp |
| `/windows/end` | `int64` | bp, `= start + L*resolution` |
| `/windows/region_type` | `uint8` | `0` = cCRE, `1` = non-cCRE, `255` = tiled |

**Biosamples** — `/biosamples` carries attr `order` = json sorted list of full biosample names.
Per biosample group `/biosamples/<NAME>/`:

| dataset | shape | dtype | notes |
|---|---|---|---|
| `counts_dsf{d}` (one per `d` in `dsf_list`) | `(n, L, F)` | `int32` | **RAW INTEGER counts.** Never arcsinh'd. See §6.1 for why not `int16`. |
| `pval` | `(n, L, F)` | `float16` | `arcsinh(-log10 p)`, always at DSF 1. Carried verbatim; the counts-only recipe never reads it. |
| `peaks` | `(n, L, F)` | `int64` | 0/1 mask. Carried verbatim. |
| `control` | `(n, L, 1)` | `float32` | control counts, DSF 1 |
| `control_meta` | `(n, 4, 1)` | `float32` | `-1` when the control is absent |
| `dna` | `(n, Lbp, 4)` | `int8` | one-hot ACGT |
| `meta_dsf{d}` (one per `d`) | `(4, F)` | `float32` | `[log2 depth, assay_id, read_length, run_type]`; **`-1`, never `0`**, for an unavailable assay or an absent DSF level |

Note `meta_dsf{d}` has **no window axis** — there is exactly one natural depth per
(biosample, assay).

**Post-bake gate.** `_verify` runs on the temp file *before* it is renamed into place, so a
poisoned bake never gets a real name (`bake.py:392-444`):

| check | assertion |
|---|---|
| F3 | rows 0-2 of every `meta_dsf{d}` are not all-zero for any column |
| F4 | `abs(meta_dsf{d}[0,c] - (meta_dsf1[0,c] - log2(d))) < 0.05` for every available column |
| F7 | counts are non-negative and `max > 50` somewhere (a double-transform would collapse the range) |
| F15 | control availability per biosample is printed; `< 100%` aborts unless `--allow-missing-control` |

### 5.4 Load-time checks

`CandiKitH5Dataset.__init__` additionally refuses a v1 file, raises when a regime produces zero
training windows, warns on a single-level DSF ladder, and — the important one — verifies that
**every column marked available in `meta_dsf1` actually carries a nonzero count** over the first
few windows (`dataset.py:169-185`). That is the tripwire for the zero-vs-`-1` poisoning in §6.6.

### 5.5 Cost, and why `/scratch`

Recorded for the q19-scale bake (8 assays, 7,485 windows):

| quantity | value |
|---|---|
| wall time | **~1.5 min per biosample** |
| on-disk (gzip-1) | **~0.16 GB per biosample** |
| dominated by | `dna` (574.8 MB uncompressed per biosample, **independent of assay count**) and `peaks` stored as `int64` for a 0/1 mask (367.9 MB — 8× waste) |
| dead weight | `pval` + `peaks` cost ~460 MB uncompressed per biosample that the counts-only recipe never reads; they are kept so the extension hook stays usable |

Source: `.BUILD_PLAN.md:776`. Scale linearly in windows and biosamples; `dna` does **not** scale
with assay count, `counts_dsf*` do.

The bake monkeypatches a per-`(biosample, chromosome)` memoization onto the chromosome-level
loaders (`bake.py:137-219`). **This is load-bearing**: without it `reference_tensors` re-reads
every `.npz` per window and the bake goes from ~15 minutes to several hours (~14M NPZ reads) for
the reference panel.

Point `--out` at a scratch filesystem. On the machine this kit was developed on, `/project` was at
23/28 TiB.

## 6. Traps

Each entry gives the symptom you will actually observe.

### 6.1 Count dtype: `int32`, and why it is not `int16`

The HDF5 `counts_dsf{d}` datasets are **`int32`** (`src/candi_kit/prep/bake.py:325`), as is the control
channel (`handler.py:1074`).

The research pipeline this kit came from used `int16` and **silently clipped** every bin above 32,767.
That ceiling is exceeded by real data: `B_DND-41`/DNase-seq reaches **52,051** reads in a single 25 bp
bin in a cCRE-sampled window. Any bake that included such a window wrote corrupted counts with no
warning. `int32` removes the ceiling; the overflow guard is kept, just at the wider bound, so an
overflow can never again be silent:

> `ValueError: count N exceeds int32 for <bios>/<assay>; re-bake with a wider dtype`

**If you see that error** you have a bin above 2,147,483,647 reads, which almost certainly means the
`.npz` is not raw per-bin counts. Check §6.2.

**Cost:** `int32` doubles the counts footprint versus `int16`. Counts are sparse and gzip-compressed, so
the effect on the h5 is much smaller than 2× in practice (the 8-assay reference panel bakes to 1.7 GB).

### 6.2 `arcsinh` is applied INSIDE the model, never by the counts loader

* `counts_dsf*` in the HDF5 and `y_data` out of the loader are **raw integers**.
* The encoder applies `arcsinh` to the signal tower input (`signal_transform='arcsinh'`).
* The NB likelihood is evaluated against **raw integer targets**.
* `pval` **is** arcsinh'd at bake time (`handler.py:1113-1117`) — that is the one exception, and it
  is not used by this recipe.

**Symptom of applying it twice:** nothing crashes. Loss descends. Macro CRPS collapses to a
plausible-looking small number on a completely different scale, and every result is
incomparable to anything else. The bake's F7 gate (`max count > 50`) catches the gross case; a
transform applied downstream of the bake will not be caught at all. **Do not transform your
counts before writing the `.npz`.**

### 6.3 RNA-seq is unconditionally excluded from the count matrix

Verbatim vendored behaviour, at all three loading sites:

* `_get_count_experiments` — `src/candi_kit/prep/handler.py:927-928`
* `load_bios_BW` — `handler.py:1084-1085`
* `load_bios_Peaks` — `handler.py:1144-1145`

```python
if "RNA-seq" in exps:
    exps.remove("RNA-seq")
```

`chipseq-control` is removed at the same sites and re-enters through the dedicated control path.

**Symptom:** if you list `RNA-seq` in `panel.assays`, the bijection assert in
`reference_sample.py:47` fires with `panel/alias mismatch: missing=['RNA-seq']`, or the column is
simply never populated. There is no flag to include it.

### 6.4 `must_have_chr_access`

`must_have_chr_access` drops any biosample lacking both ATAC-seq and DNase-seq
(`handler.py:886-888`). It defaults to `False` (`handler.py:1671`) and it is set only inside
`setup_datalooper` (`handler.py:1696`), which the kit never calls. On the kit's EIC-only path
(`self.eic = True`) the branch containing it is **unreachable** — the `T_`/`V_`/`B_` prefix filter
takes the `if` arm at `handler.py:876`. Recorded here because the code is visible and reads like a
live filter: if you re-enable the non-EIC path, it will silently delete biosamples with no error
message.

### 6.5 **The shipped blacklist BED is a placeholder — say it out loud**

`data/hg38_blacklist_v2.bed` in the research repo is **8 bytes containing the single line
`# Empty`**. `_load_blacklist` skips `#` lines (`handler.py:219-220`), so it parses to zero
intervals and **no blacklist filtering happens at all**. The same is true if you omit
`--blacklist`.

**You must supply a real ENCODE blacklist BED via `--blacklist`** if you want blacklist exclusion.
The kit warns, once, on stdout (`src/candi_kit/prep/paths.py:29-31`):

```
WARNING: blacklist empty (None) -> 0 regions excluded
```

**Symptom if you miss it:** the bake succeeds; training succeeds; a small number of windows sit on
high-signal artifact regions and inflate both your loss and your evaluation. Nothing else tells
you.

Note the blacklist is consulted only through `_is_region_allowed`, i.e. for **type-2 locus
sampling** (`bake.py:83-86`). Plain chromosome tiling of `train_chroms`/`eval_chroms` does not
consult it.

### 6.6 `meta_dsf` must be `-1`, never `0`, for an absent level

The dataset's availability test is literally `float(meta[0]) != -1.0`
(`dataset.py:306, 314`). A zero-filled metadata row therefore marks **every** assay available at
`log2(depth) = 0`, `assay_id = 0`, `read_length = 0`, with all-zero counts. The bake writes `-1`
(`bake.py:376-379`) and the loader tripwires on it (`dataset.py:169-185`):

> `ValueError: T_X/H3K4me3 is marked available in meta_dsf1 (log2 depth 0.0) but counts_dsf1 is
> all-zero over 4 windows — the h5 is poisoned ...; re-bake.`

**Symptom without the tripwire:** training proceeds, the loss descends, and every metric is
garbage. This is why the kit refuses schema v1 files outright.

### 6.7 DSF only downsamples — there is no upsampling regime

Every `signal_DSF{d}` level is produced by Bernoulli read-retention from the full BAM, so the
training depth support for an assay is `[natural_min - 3, natural_max]` in `log2` units. There is
no mechanism, in the data or the code, that presents the model with a *deeper* target than it has
observed.

Consequences you must carry into any depth-steering claim:

* **7 of the 12 held-out evaluation targets in the reference panel sit above their per-assay
  training depth ceiling** (worst `+1.43 log2`), so depth steering on them is extrapolation in the
  untrained direction (`METADATA_AUDIT.md:115, 253`).
* The DSF levels are **not a nested ladder** — `dsf4 <= dsf2` is False; they are independent draws,
  so `counts ∝ 1/dsf` holds only in expectation (`METADATA_AUDIT.md:87`).
* A `dsf_list` with a single level makes per-assay independent `x_dsf != y_dsf` inert and removes
  the depth signal entirely. Both the panel (`panel.py:44-48`) and the dataset
  (`dataset.py:163-165`) warn.

### 6.8 `run_type` is analytically unidentifiable on the shipped 8-assay panel

On the reference training slice, `H(run_type | assay_id, read_length) = 0.000 bits` (n = 26):
`run_type` is a deterministic function of the other two covariates, so nothing can be learned from
it that is not already available for free (`METADATA_AUDIT.md:242`). **A `run_type` steering demo is
impossible on that panel** — this is a property of the data, not of the architecture. The full EIC
panel retains **0.551 bits** after conditioning on assay, so a re-selected biosample panel that
breaks the `run_type ⟂ (assay, read_length)` degeneracy is the fix. If `run_type` steering matters
to you, select your biosamples for it deliberately.

Related, and also a data property: depth, `read_length` and `run_type` are mutually collinear at
n = 38 (assay-centred `corr(depth, log2 rl) = 0.763`, `corr(depth, rt) = 0.590`,
`corr(log2 rl, rt) = 0.697`), so attribution among the three exposure covariates is not identified
on a panel of this size (`METADATA_AUDIT.md:251`).

### 6.9 An absent DSF level is skipped, not silently substituted

Upstream, an assay missing from an explicit DSF map loaded DSF-1 counts and paired them with
DSF-1 depth metadata — a lie the depth objective then learned from. The kit skips the assay
instead (`handler.py:1017-1022`, edit E3). **Symptom:** an assay you expected simply does not
appear in that DSF level and is marked `-1`; the F4 gate (§5.3) would otherwise have caught the
mismatch at bake time.

## 7. Bringing your own data

### 7.1 Minimal checklist

1. **Directory shape.** `<ROOT>/<BIOSAMPLE>/<ASSAY>/` exactly as in §1. Biosample names start with
   `T_`, `V_` or `B_`; held-out views share the suffix with their `T_` (`T_X` ↔ `V_X` / `B_X`).
2. **At least 2 `T_` biosamples, each with ≥ 2 assays present.** Fewer and imputation supervision
   is identically zero.
3. **Counts.** One `.npz` per chromosome per DSF level, whole-chromosome, raw integer counts at
   `resolution` bp, length `ceil(chr_len / resolution)`. Single array per file.
4. **DSF levels.** Produce all levels in `dsf_list` by actual read subsampling. Each level needs
   its own `metadata.json` with the **subsampled** `depth`. If `meta_dsf{d}[0]` does not equal
   `meta_dsf1[0] - log2(d)` to within 0.05, the bake aborts.
5. **`file_metadata.json`** per assay directory, with `read_length` and `run_type` as
   single-entry dicts. `run_type` strings must contain `single` or `pair`.
6. **`signal_BW_res{r}/` and `peaks_res{r}/`** per assay, whole-chromosome, length
   `floor(chr_len / resolution)`. These are not used by the counts-only recipe but the bake reads
   them unconditionally.
7. **`chipseq-control/`** per biosample, with its own `file_metadata.json` (replicate key `"2"`)
   and `signal_DSF{d}_res{r}/`. If you cannot supply it everywhere, pass
   `--allow-missing-control` and accept that the model loses a channel it can never mask.
8. **Do not create `aliases.json` or `navigation.json` by hand.** Let the first bake generate them,
   then never delete them — a checkpoint is only valid against an HDF5 whose recorded assay order
   matches.
9. **Side files.** Real `--chrom-sizes`, real `--fasta` + `.fai`, and a **real** `--blacklist`.
10. **Write the panel JSON** (§4.1) and bake to `/scratch`.

## 8. What this model does and does not consume

* **Counts-only.** The shipped decoder emits a **Negative Binomial** `(n̂, p̂)` per assay per bin.
  There is **no Gaussian p-value head and no Bernoulli peak head** in this kit, therefore no peak
  precision/recall/AUROC and no p-value track in the results. `pval` and `peaks` are baked and
  carried through the batch dict purely so the extension hook remains wireable — see
  `EXTENSION_HOOKS.md`.
* **DNA is mandatory.** The encoder always builds and calls the DNA tower; there is no
  counts-without-sequence configuration.
* **Four covariates, raw.** `[log2 depth, assay_id, read_length, run_type]`, no normalization.

For what the two shipped training arms (`--offset on` / `--offset off`) actually buy you, and the
honest noise floor around every recorded number, read `TRADEOFF.md` before quoting any result.
